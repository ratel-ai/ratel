# `lib/console` (L6)

Console helpers above ingest and the catalog: navigation, shell data, sidebar state, command
search, projects, settings, and development seeds.

| Path | Holds |
|---|---|
| `navigation.ts` | the rail model: project URLs, the destinations this build has (inside a project its pages; outside one the organization's Projects, Integrations and Settings) plus `composition.nav` and the edition's project groups (a section, or a collapsible row in the setup group, as Cloud's APIs row), grouped into Monitor, Insights, Improve and Ship for everyone, as upstream (RC-270: the Ship page, and Tasks as a top-level page under Insights in place of Agent health › Tasks), the active item (an item is also lit on the paths it lists in `also`, and a child can light its parent through `activeId`), Traces' children (All traces, then Sentiment analysis with `sentimentAnalysis` on for the shown organization, then Agents and MCP servers with `agentsPages`; Root cause analysis is in no menu: task completion on Agent health opens it and lights Agent health), Agent health's children (Summary, Self-corrections, then Hallucinations with `hallucinationDetection` on for the shown organization), the organization the shell shows (`shellOrganization`, upstream's: the open project's own, else the route's, else the active one), project switching, the ⌘K entries (the rail with its keywords, the pages one level down, the organization's pages from inside a project, the projects), where `/dashboard` lands |
| `command-actions.ts` | the ⌘K actions: the edition's (`EditionUi.commandActions`, each dispatching its window event) before Keyboard shortcuts and the sidebar toggle |
| `scope/command-search.ts` | the ⌘K ranking |
| `scope/project-scope.ts` | one project of any organization the reader belongs to, with their role there, or a 404 (upstream's rule: membership in the project's own organization; the active one is never consulted) |
| `scope/organization-scope.ts` | the same for an organization page or action, by slug: every `/org/<slug>` page, the New project action and `/onboarding?organization=` read it |
| `scope/legacy-redirects.ts`, `scope/moved-pages.ts` | upstream's old-address rules: `/traces`, `/explore`, `/experiments`, `/settings`, `/embeddings` to their project pages, `/billing` and `/members` to the organization's, and the pages the redesign folded into others |
| `scope/legacy-route.ts` | new here: those two rules chained for a console route, since this edition has no proxy to answer them (ADR-0003). `/billing`, `/members` and `/embeddings` land on pages only an edition has, so their routes answer 404 without one |
| `scope/sentinel.ts`, `scope/landing.ts`, `scope/cookie.ts` | `/project/_/…`, the last project a reader was in (owned: the cookie only, checked against the organizations the reader belongs to; the pointer upstream keeps on the user is the edition's, through `SessionPort.rememberProject`) and the cookie that remembers it |
| `scope/remember-project.ts` | new here: writes that cookie when a project page is opened and it names another project, from a server action the project layout asks for (upstream's proxy does it; no proxy here, ADR-0003); `openProject`, the layout's order: the scope check, then the edition's `SessionPort.rememberProject` (upstream's `users.last_project_id`) |
| `stale-build.ts` | a server action the server no longer knows (a tab from before a deploy) is named as such, with a reload offer (`components/console/stale-build-callout.tsx`); `next.config.ts` sets `deploymentId` from `NEXT_DEPLOYMENT_ID`, so a navigation from an older tab reloads first |
| `project-settings.ts` | renaming a project of any organization where the reader is an admin; a changed name is reported as `project_settings_updated` |
| `start-project-creation.ts` | where "New project" goes (owned port of upstream's action): onboarding for the organization (any the reader belongs to; unlike upstream it does not become the active one), or back to the projects page with `?limit=projects` at the plan's cap |
| `onboarding/` | the project-creation flow at `/onboarding`, for the first project and every later one: `create-first-project.ts` (new here: the project and its Default key in one step, refused in a support session or at the plan's cap; the key goes to an edition that keeps keys, and `key-note.ts` words the reveal accordingly), `core-service.ts` (new here: the same step, the snippets and the sample project as `CoreServices.onboarding`, lent to the edition at startup for a page it owns; the edition answers for the session), `quickstart.ts` (upstream's send-your-first-trace snippets: the Cloud SDK's span processor pointed at the endpoint it is given, and curl), `capture-consent.ts` (the "What Ratel will read" copy, a promise about users' data) `transition.ts` (the exit timings) and `arrival-veil.ts` (the veil the route change goes under, lifted once the console has its content, so it fades in instead of popping); the sample project: `provision-sample.ts` (owned port of upstream's demo provisioning: an organization with no projects and no `sample_project_seeds` row gets Site Copilot once, inline from `shell-data.ts`, the mark claimed before the seed so a failed or deleted sample never returns), with its `schema.ts` and `queries.ts` The guided tour's model is here too: `tour-steps.ts` (what it says and the `data-tour` anchors it points at), `tour-geometry.ts`, `tour-state.ts` (upstream's), `tour-status.ts` (new here: where how a person left the tour is kept, the edition's `SessionPort.tourStatus` when it has one, upstream's users table, else the cookie; `app/(console)/tour-actions.ts` writes through it and the project home reads through it) and `tour-cookie.ts` (new here: the open-source keeping, a per-browser cookie, `ratel_tour_status`). Not seeded in an admin support session, as upstream. |
| `settings/` | the settings tabs (`organization-tabs.ts`: Danger zone for admins only, where the edition has the page, as upstream), the API key rows, the SDK events views and payload read, the redirect settle helper, the projects list model and UTC date formats; `support-session-ui.test.ts`: the API keys and Danger zone disabled in an admin support session |
| `delete-project.ts` | deleting a project of any organization the reader belongs to once its name is typed back, refused in a support session; the next page is in that project's own organization; a delete is reported as `project_deleted` |
| `catalog/` | the Catalog pages' models: the tool and skill rows, the tree, search, paging, the loaders |
| `explore/` | the browser client for the skills API, its form payloads and error copy |
| `shell-data.ts` | the session organization and its projects, and every organization the reader belongs to with theirs (upstream's navigation data), once per request, for the shell and the pages; the account's name falls back as upstream's (name, username, email, "Account") and carries the session's profile photo |
| `sidebar-cookie.ts` | the persisted collapse state of the sidebar |
| `loading-skeletons.test.ts` | the catalog and organization skeletons' markup, and that the catalogs, playground, trace compare and organization MCP routes each have a `loading.tsx` drawing their own page's skeleton, as upstream |
| `wiring.test.ts` | source checks for what a page renders or a route calls where no unit test can run the page (the sidebar freshness line, the tour offer, the API keys quickstart, run to test, the SDK event links, the last-project request, the no-database layout, one ingest address builder, project scope in two routes, root metadata, jobs in the project log context, the playground heading), and the capture nudge against the quickstart |
| `seed/` | local-database guard, seed organization and project replace, seed command-line args, Site Copilot OTLP and catalog fixtures, and `site-copilot-seed.ts`: the seed itself (the project, its key and catalog, the traces through the route handler, the queued ledger build), shared by the seed script and the sample provisioner; `settle-queue.ts`: after each of the seed's drain ticks, waits for a job a worker is running and drains what is left queued, so the result does not depend on a worker; `task-loop.ts`: the task loop demo, run through the production jobs (live scores, eval sets, a draft, two simulations, a shipment and its post-ship measure), with its PGlite test |

`pnpm --filter @ratel/platform seed` runs `scripts/seed.mts`, which writes Site Copilot through the
traces handler into a local Postgres and drains the jobs it queued. On a fresh database it first provisions the operator's
organization, as a first console visit would. `pnpm --filter @ratel/platform seed:task-loop --project
<id or slug> [--no-models]` runs `scripts/seed-task-loop.mts` on a project the seed built (with
`--drain`): the task loop demo; `--no-models` uses the local stand-ins and calls nothing out.
Copies and owned files are listed in
`scripts/platform-sync/map.json`.
