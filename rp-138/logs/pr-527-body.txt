## What

- **RC-779: detection source marker.** Each agent, MCP server and client shows how Ratel detected it. A guess (heuristic source) shows a **Guessed** badge on the Agents list and detail, the MCP servers list and detail, and the Clients tab. Its tooltip names the rule that matched (from service.name, from the agent span name, from the tool name prefix, from the User-Agent header) and the attribute that makes it explicit. SDK and OpenTelemetry detections show no warning: detail pages show a neutral "Ratel SDK" or "OpenTelemetry" badge. An entity with mixed sources shows its weakest source (SQL `min` over a rank). One component: `components/ds/detection-marker.tsx`. Rules and fix text: `lib/entities/detection.ts`.
- **RC-780: MCP server setup guide, standard OpenTelemetry, no SDK.** A guide on the MCP servers and Clients tabs (open on an empty list), and in `get_sdk_setup` as `mcpServer` when `cloud-project-entities` is on. Python (`mcp` 2.x native spans + ASGI HTTP span) and TypeScript (`@modelcontextprotocol/sdk` 1.x with one semconv span per request + HTTP instrumentation). The fact table is built from the ingest key constants in `lib/otlp/dimensions/`, so it cannot drift. It states the stdio and stateless HTTP limits and how to send no client IP (ASGI wrapper, or a Collector attributes processor).

All new surfaces stay behind `cloud-project-entities` (off by default).

## Notes

- The TypeScript snippet wraps requests by hand: the MCP TS SDK's native OpenTelemetry is merged upstream but not in an npm release yet.
- Known ingest quirk, not changed here: the HTTP server span of an MCP server gets its `service.name` as an agent key, so the server also lists as a guessed agent.
- `list_agents`, `list_mcp_servers` and `list_clients` do not return the detection source yet.
